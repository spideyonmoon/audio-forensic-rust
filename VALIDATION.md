# Version 0.1 core validation — 2026-09-30

This records checks actually run on the Windows development host. The implemented
engine is a decoding/measurement subset, not the full Python forensic suite.
Nothing here establishes classification accuracy or genuine source history.
The later version 0.2 checks are in [DETECTOR_VALIDATION.md](DETECTOR_VALIDATION.md);
the figures below are preserved as the initial measurement-only baseline.

## Build and automated checks

- Rust/Cargo 1.98.1, Windows x86_64 GNU toolchain; project-local installation.
- Release executable built successfully at `target/release/audio-forensic.exe`.
- 15 Rust integration tests passed: 13 core/CLI tests and 2 parity/integrity tests.
- `cargo fmt --all -- --check` passed.
- `cargo clippy --locked --all-targets -- -D warnings` passed.
- Android ARM64 library compilation check passed using
  `cargo check --lib --no-default-features --target aarch64-linux-android --locked`.
  This is a Rust target check, not NDK linking, an APK build, or an on-device test.
- GitHub Actions configuration was added for Windows/Linux tests and an Android
  library check; remote CI has not been run from this workspace.

The core/CLI tests exercise bit preservation at 16/24/32 bits, conservative
padding observations, stray low bits, silence, short input, exact STFT boundaries,
shared prefix limits, invalid options, cancellation/deadline outcomes, unsupported
surround, float PCM applicability and nonfinite rejection, truncated WAV, missing
tracks, anti-phase channels and continuing a batch after a missing input file.

## Python baseline and numerical agreement

Reference commit: `c6ecce2296256b516709d87088896d1be913908c`.

- `python -X utf8 test_dsp.py`: 79/79 checks passed.
- `python -X utf8 -m unittest -v test_accuracy test_vorbis test_mqa`: 22 tests
  passed, no skips, including the synthetic encoder regressions.
- Environment: NumPy 2.3.5, SciPy 1.17.1 and FFmpeg 7.1.1 (Gyan Windows build).

Three generated stereo signals (full-band noise, a 15 kHz lowpass with integer
padding, and silence/quiet/active sections) are stored in both WAV and FLAC.
All six fixtures decode to the independently calculated original PCM SHA-256.
Their per-channel streaming features agree with numerical oracles generated by
the pinned Python methods at the explicit tolerances in `tests/parity.rs`.
For example, cutoff and cutoff variance have 0.01 absolute tolerances in their
respective units, dB features 0.02 dB, magnitude ratio 1e-6, and entropy 1e-5.

Truncated FLAC and a deliberately wrong STREAMINFO checksum both return failures.
The parity tests exposed retained checksum state after decoder reset; creating a
new decoder per pass fixed it. Both successful full passes are verified, and their
decoded-sample hashes must agree.

Fixture generators are versioned. Regeneration requires the clean pinned Python
checkout; ordinary Rust tests use the saved fixtures without Python or FFmpeg.

## Supplied music files

All 25 FLAC files present in `reference/test_files` at the start of the run were
examined, without changing them. They are described by the user as CD/vinyl rips;
that description is not an independently established ancestry label.

- **22 files:** full-stream analysis succeeded. Every decoded PCM SHA-256 matched
  an independent FFmpeg decode exactly; stream lengths matched their headers and
  decoder checksum verification succeeded.
- **3 files:** full-stream analysis returned a structured error and did not
  prevent later files from being processed. FFmpeg independently reported invalid
  sync/frame headers for all three with `-xerror` enabled.

| File | Header frames | Decoded frames | Deficit relative to header |
| --- | ---: | ---: | ---: |
| 01 - Hands Up.flac | 9,517,956 | 9,515,520 | 2,436 |
| 11 - The APL Song.flac | 7,713,384 | 7,709,184 | 4,200 |
| 13 - Where Is The Love.flac | 12,620,832 | 12,616,704 | 4,128 |

These are file-integrity findings, not evidence that those recordings were lossy
transcodes. The files were not repaired or re-encoded. The local validation
command exits 1 because three inputs fail its success criteria; this is separate
from the passing automated code tests.

The successful collection covers 16/24-bit PCM and 44.1/88.2/96 kHz. Track lengths
range from approximately 96 to 713 seconds. This release core took 1.32-7.89
seconds per successful file and used 12.68-29.80 MiB peak working set. These are
observations on this Windows host, with filesystem caching and other activity,
not mobile benchmarks or performance claims for the unimplemented full suite.

A separate first-60-seconds run of Hands Up succeeded and matched FFmpeg on that
interval. Its report explicitly says the end of the file was not reached and
does not claim full-file integrity. This checks that the prefix contract remains
distinct from the failing full-file integrity check.

## Duration and memory check

`scripts/check_resources.py` generated stereo 16-bit/48 kHz WAVs of increasing
duration using a fixed-size signal block. Full analysis and independent FFmpeg
PCM hashes passed for all three.

| Duration | Peak working set | Analysis process wall time |
| --- | ---: | ---: |
| 10 seconds | 12.83 MiB | 0.31 seconds |
| 120 seconds | 12.10 MiB | 1.61 seconds |
| 600 seconds | 12.96 MiB | 7.99 seconds |

The roughly constant measured footprint is consistent with the bounded DSP
buffer design. Windows OS-reported process peak working set was sampled every
10 ms while the process ran; measurements can vary across runs. This is not a
hard cap on decoder/container allocations or a hostile-input security audit.
Raw data: `corpus/local/results/resource-check/summary.json`.
